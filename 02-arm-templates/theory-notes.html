Section 01

What is Azure Resource Manager (ARM)?

Azure Resource Manager is the deployment and management service for Azure. Every action you take in the portal, CLI, or PowerShell goes through ARM. ARM Templates let you describe your infrastructure in a JSON file — and Azure will create or update it to match.

Why use ARM Templates?

  • Repeatability — deploy the same environment 100 times, same result every time
  • Version control — store templates in Git, track changes over time
  • No manual errors — no clicking through portal steps that you might forget
  • Idempotent — running the same template twice doesn't break things; it checks existing state
Analogy
An ARM Template is like a blueprint for a building. The blueprint describes every room, wall, and pipe. You give it to a contractor (ARM), and they build exactly what's described — whether it's your first or tenth building.

Section 02

ARM Template Structure

An ARM template is a JSON file with a specific structure. It must have a $schema and a resources section at minimum.

$schema

Schema

Tells Azure which schema/version of the template language to use. Always required.

contentVersion

Version

Your own version string, e.g., "1.0.0.0". Not used by Azure, just for your tracking.

parameters

Parameters

Values you provide at deploy time — e.g., VM name, location. Makes templates reusable.

variables

Variables

Computed values used inside the template. Avoids repeating the same expression.

resources

Resources

The main section — what you're actually deploying (VMs, storage accounts, VNets, etc.).

outputs

Outputs

Values returned after deployment, e.g., the public IP or connection string.

Minimal ARM Template

// Minimal ARM template — creates one Storage Account { "$schema": "https://schema.management.azure.com/schemas/2019-04-01/deploymentTemplate.json#", "contentVersion": "1.0.0.0", "parameters": { "storageAccountName": { "type": "string", "metadata": { "description": "Name of the storage account" } } }, "resources": [ { "type": "Microsoft.Storage/storageAccounts", "apiVersion": "2023-01-01", "name": "[parameters('storageAccountName')]", "location": "[resourceGroup().location]", "sku": { "name": "Standard_LRS" }, "kind": "StorageV2" } ] }
Section 03

Parameters & Variables

Parameters — input values at deploy time

Parameters let you pass different values each time you deploy. For example, use the same template for Dev and Prod by passing different VM sizes.

"parameters": { "vmSize": { "type": "string", "defaultValue": "Standard_B2s", "allowedValues": ["Standard_B1s", "Standard_B2s", "Standard_D2s_v3"], "metadata": { "description": "Size of the virtual machine" } }, "environment": { "type": "string", "allowedValues": ["dev", "staging", "prod"] } }

Variables — reusable computed values

Variables let you compute values once and reference them many times. Keeps templates clean.

"variables": { "storageAccountName": "[concat('st', parameters('environment'), uniqueString(resourceGroup().id))]", "location": "[resourceGroup().location]" }
Parameters vs. Variables
Parameters come from outside (you provide them at deploy time). Variables are calculated inside the template. Use parameters for things that change between environments; variables for things computed from parameters.
Section 04

Resources Section

The resources array is the core of the template — it lists every Azure resource to create or update.

Resource Block Structure

{ "type": "Microsoft.Compute/virtualMachines", // resource provider/type "apiVersion": "2023-09-01", // API version of the resource "name": "[parameters('vmName')]", // resource name "location": "[resourceGroup().location]", // where to deploy "dependsOn": [ // deploy AFTER these "[resourceId('Microsoft.Network/networkInterfaces', variables('nicName'))]" ], "properties": { // resource-specific config ... } }

dependsOn

Azure tries to deploy all resources in parallel by default. Use dependsOn to tell ARM "this resource needs another one to exist first." For example, a VM depends on its NIC, which depends on the VNet.

API Version
Each resource type has its own API version. Always check the latest at learn.microsoft.com/azure/templates. Using an old API version means you might miss new features.

Template Functions

ARM templates have built-in functions you can use in expressions (inside square brackets [ ]).

FunctionWhat it doesExample
parameters('name')Gets a parameter value[parameters('vmName')]
variables('name')Gets a variable value[variables('location')]
resourceGroup().locationCurrent RG's region[resourceGroup().location]
concat(a, b)Joins strings together[concat('vm-', parameters('env'))]

Section 06

Deployment Methods

You can deploy an ARM template in four ways:

Azure Portal

Deploy > Template Deployment > upload JSON. Good for learning and quick one-offs.

Azure CLI

az deployment group create

Best for scripts and CI/CD pipelines on Linux/Mac.

PowerShell

New-AzResourceGroupDeployment

Windows-friendly. Good for automated scripts.

GitHub Actions / DevOps

Use azure/arm-deploy action. Ideal for automated deployments on every push.

CLI Deployment Example

# Deploy a template to a resource group az deployment group create \ --resource-group rg-myapp-dev \ --template-file main.json \ --parameters vmName=myVM environment=dev
Section 07

Bicep — The Modern Alternative to ARM JSON

Bicep is Microsoft's domain-specific language (DSL) for ARM templates. It compiles down to ARM JSON, so everything ARM can do, Bicep can do — but with much cleaner syntax.

ARM JSON vs. Bicep — Same Storage Account

ARM JSON (verbose)
{
  "type": "Microsoft.Storage/storageAccounts",
  "apiVersion": "2023-01-01",
  "name": "[parameters('storageName')]",
  "location": "[resourceGroup().location]",
  "sku": { "name": "Standard_LRS" },
  "kind": "StorageV2",
  "properties": {}
}
Bicep (clean)
resource storage 'Microsoft.Storage/storageAccounts@2023-01-01' = {
  name: storageName
  location: resourceGroup().location
  sku: { name: 'Standard_LRS' }
  kind: 'StorageV2'
}

Bicep Advantages

  • Much less verbose — no $schema, no square-bracket expressions
  • Native type safety — editor catches errors as you type
  • Modules — split large templates into reusable files
  • Microsoft recommends Bicep for all new projects over ARM JSON
For AZ-104 Exam
The exam tests ARM template concepts (structure, parameters, functions). You don't need to memorize Bicep syntax, but know that Bicep compiles to ARM JSON and is the preferred way to write IaC on Azure today.
Section 08

Summary — Key Points

ARM

Deployment & management layer for ALL Azure resources. Portal, CLI, PowerShell all go through ARM.

Template Sections

$schema, contentVersion, parameters, variables, resources, outputs.

Parameters

Input at deploy time. Makes templates reusable across Dev/Staging/Prod.

Variables

Computed values inside the template. No user input needed.

dependsOn

Forces sequential deployment. ARM deploys in parallel by default.

Bicep

Cleaner syntax, compiles to ARM JSON. Preferred for new projects.
