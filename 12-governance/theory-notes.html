Section 01

Azure Governance Hierarchy

Azure resources are organized in a four-level hierarchy. Policies and RBAC assignments at a higher level are inherited by all children below.

Management Group
Groups subscriptions; apply policy across the entire organization
↳
Subscription
Billing unit; trust boundary; quota limits per subscription
   ↳
Resource Group
Logical container for related resources; lifecycle management
      ↳
Resource
Individual service: VM, Storage Account, VNet, etc.

Governance controls (RBAC, Azure Policy, Locks, Tags) can be applied at any level and flow down through inheritance.

Section 02

Subscriptions & Accounts

A subscription is the primary billing and deployment boundary in Azure. Every resource you create belongs to a subscription.

  • Account: The identity that signs up and owns subscriptions (Entra ID account or Microsoft Account).
  • Subscription types: Free Trial, Pay-As-You-Go, Enterprise Agreement (EA), CSP (Cloud Solution Provider), Dev/Test.
  • Quota limits: Each subscription has limits (e.g., 25,000 VMs/region). You can request increases via Support.
  • Trust: A subscription trusts exactly ONE Entra ID tenant for authentication.
Subscriptions are also cost boundaries — each gets its own bill. Enterprises use separate subscriptions per team, environment (prod/dev), or geographic region for cost isolation.
Section 03

Management Groups

Management Groups are containers that help you organize multiple subscriptions and apply governance at scale. Policies assigned to a management group automatically apply to all subscriptions within it.

  • The top-level group is the Root Management Group — all subscriptions belong to it.
  • Up to 6 levels of nesting (excluding root and subscription levels).
  • One subscription can only belong to ONE management group at a time.
  • Example structure: Root → Corp → Finance → Prod-Finance-Sub
Assign Azure Policy and RBAC roles at the management group level to ensure consistent governance across all subscriptions in your organization — no need to repeat it per subscription.
Section 04

RBAC — Role-Based Access Control

Azure RBAC controls who can do what on which Azure resources. It uses role assignments — granting a security principal (user, group, service principal) a specific role at a specific scope.

Role Assignment = Who + Role + Scope

ComponentDescriptionExample
Who (Security Principal)User, group, service principal, managed identityjohn@contoso.com
Role (Definition)A collection of permissionsVirtual Machine Contributor
ScopeManagement Group → Subscription → Resource Group → ResourceResource Group: rg-production

Built-in Roles

RolePermissionsUse case
OwnerFull control + manage accessSubscription owner
ContributorFull control (create/delete) but cannot manage accessDev team lead
ReaderView only, no changesAuditors, finance
User Access AdministratorManage user access onlyIT helpdesk
VM ContributorManage VMs but not VNet or StorageVM-specific admins

Custom Roles

When built-in roles don't fit exactly, you can create custom RBAC roles by specifying exactly which actions are allowed (Actions), denied (NotActions), and data-plane actions (DataActions). Stored in Entra ID, assignable across subscriptions in the same tenant.

RBAC is additive — if a user has Reader at subscription and Contributor at resource group, they get Contributor at that resource group. Deny assignments (rare) are the only way to explicitly block access.
Section 05

Azure Policy

Azure Policy enforces organizational standards and assesses compliance across your Azure environment. Unlike RBAC (who can do what), Policy controls what configurations are allowed.

RBAC

Controls who can take actions

e.g., "Only Admins can create VMs"

Azure Policy

Controls what configurations are allowed

e.g., "All VMs must be in East US region"

Policy Effects

EffectWhat it does
DenyBlocks the resource creation/update if it violates policy
AuditAllows creation but logs a warning for compliance reporting
AppendAdds required fields (e.g., auto-add tags) during resource creation
DeployIfNotExistsAuto-deploys a related resource if missing (e.g., install monitoring agent on VM)
ModifyAdd, update, or remove properties on existing resources

Initiatives (Policy Sets)

An Initiative groups multiple policy definitions into one assignment — e.g., the "Enable Azure Monitor for VMs" initiative contains 5 policies to deploy agents, configure diagnostics, etc.

Azure provides built-in initiatives for compliance standards: ISO 27001, NIST, PCI DSS, CIS Benchmark. Assign them to assess your environment's compliance posture.
Section 06

Cost Management

Azure Cost Management + Billing helps you monitor, analyze, and optimize your Azure spending.

Key Tools

ToolPurpose
Cost AnalysisVisual breakdown of costs by service, resource group, tag, time period
BudgetsSet spending thresholds; get email alerts at 50%, 80%, 100% of budget
Advisor RecommendationsAzure Advisor suggests cost savings (right-size VMs, buy reservations)
Pricing CalculatorEstimate costs before deploying (azure.microsoft.com/pricing/calculator)
TCO CalculatorCompare on-premises vs Azure total cost of ownership

Cost Optimization Tips

  • Reserved Instances: Pre-pay for 1 or 3 years — up to 72% savings vs Pay-As-You-Go.
  • Azure Hybrid Benefit: Use existing Windows Server / SQL Server licenses in Azure — up to 40% savings.
  • Auto-shutdown VMs: Schedule dev/test VMs to stop at night.
  • Right-sizing: Downsize VMs that consistently run at low CPU.
  • Spot VMs: Use spare Azure capacity for batch/interrupt-tolerant workloads — up to 90% off.
Section 07

Resource Tags

Tags are name-value pairs attached to Azure resources for organization, cost allocation, and automation.

Tag ExampleValuePurpose
EnvironmentProduction / Dev / StagingFilter resources by environment
CostCenterFinance / Marketing / ITChargeback billing by department
Ownersahil@cloudsynq.shopIdentify who owns the resource
ProjectERP-MigrationGroup resources by project
  • Up to 50 tags per resource.
  • Tags are NOT inherited — tagging a Resource Group does not auto-tag its resources (use Azure Policy to enforce inheritance).
  • Use tags in Cost Analysis to see spending per project or department.
Create an Azure Policy with the "Append" effect to automatically add required tags (e.g., Environment, CostCenter) to all new resources — prevents untagged resources.
