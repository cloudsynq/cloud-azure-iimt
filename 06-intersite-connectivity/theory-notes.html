Section 01

Why Intersite Connectivity?

Azure VNets are isolated by default. Resources in VNet-A cannot communicate with VNet-B, and your on-premises office cannot reach your Azure VMs — unless you explicitly connect them. Intersite connectivity options solve this.

VNet ↔ VNet

Connect two Azure VNets (same or different regions/subscriptions)

On-Premises ↔ Azure

Connect your office/datacenter to Azure over internet (VPN) or private line (ExpressRoute)

Hub-Spoke Topology

One central hub VNet connects to many spoke VNets — shared services model

Section 02

VNet Peering

VNet Peering connects two VNets using Microsoft's backbone network (not the public internet). Traffic is private, low-latency, and high-bandwidth.

Regional Peering

  • Same Azure region
  • Lowest latency
  • No gateway required
  • Inbound/outbound data charged

Global VNet Peering

  • Different Azure regions
  • Cross-region private connectivity
  • Slightly higher cost than regional
  • Same benefits as regional

Key Rules

  • Peering is non-transitive — if A↔B and B↔C, A cannot reach C automatically. You must peer A↔C separately (or use Azure Virtual WAN / hub).
  • Address spaces must not overlap between peered VNets.
  • Peering is a two-way link — you must create peering from both sides (A→B and B→A).
  • Peering can span different subscriptions and tenants (with proper permissions).
VNet Peering is the cheapest and fastest way to connect two Azure VNets. No gateways, no VPN, no public internet — just Microsoft's backbone.

Use Allow Gateway Transit

In a hub-spoke model, spoke VNets can use the hub's VPN/ExpressRoute gateway by enabling Use Remote Gateways (spoke) and Allow Gateway Transit (hub) on the peering settings.

Section 03

VPN Gateway

An Azure VPN Gateway creates an encrypted tunnel over the internet between your on-premises network (or another VNet) and your Azure VNet. Uses IPsec/IKE protocols.

Types of VPN Connections

TypeUse CaseRequires
Site-to-Site (S2S)Office/datacenter to Azure — always-onOn-prem VPN device with public IP
Point-to-Site (P2S)Individual laptops to Azure VPNVPN client software on laptop
VNet-to-VNetTwo Azure VNets via VPN (older method, prefer peering)Gateway in each VNet

SKUThroughputTunnelsBest for

VPN Gateway can take 30–45 minutes to provision. It requires its own dedicated subnet named exactly GatewaySubnet (minimum /27).

Active-Active vs Active-Passive

  • Active-Passive (default): One instance active, one standby. Failover in 10–15 seconds.
  • Active-Active: Both instances active simultaneously. Higher availability, requires BGP.
Section 04

ExpressRoute

ExpressRoute provides a dedicated private connection from your on-premises datacenter to Azure — bypassing the public internet entirely. Traffic never traverses the internet.

VPN Gateway

  • Over the internet (encrypted)
  • Max ~10 Gbps
  • Variable latency
  • Lower cost
  • Suitable for most workloads

ExpressRoute

  • Private line (not internet)
  • Up to 100 Gbps
  • Predictable, low latency
  • Higher cost
  • Banks, healthcare, compliance

ExpressRoute Circuit

You work with a connectivity provider (Airtel, Tata, Equinix, etc.) who physically connects your datacenter to a Microsoft Edge location. Microsoft peering types:

  • Private Peering: Access to Azure VMs and services (VNets) — most common.
  • Microsoft Peering: Access to Microsoft 365, Dynamics 365, Azure PaaS services.
ExpressRoute circuits have an SLA of 99.95%. For 99.99% availability, deploy two circuits from different providers (ExpressRoute Global Reach).
Section 05

Custom Routes & User-Defined Routes (UDR)

Azure automatically creates system routes for VNet traffic. But you can override them with User-Defined Routes (UDR) — for example, to force all traffic through a firewall or NVA (Network Virtual Appliance).

Common Use Cases

  • Force all internet-bound traffic through Azure Firewall for inspection.
  • Route traffic between subnets through an NVA (Palo Alto, Fortinet, etc.).
  • Override BGP routes learned from on-premises.

Route Priority Order

  1. User-Defined Routes (highest priority)
  2. BGP Routes (from VPN/ExpressRoute)
  3. System Routes (Azure default)
Next hop types: VirtualAppliance | VirtualNetworkGateway | VNetLocal | Internet | None
Attach route tables to subnets, not individual VMs. All VMs in a subnet follow the same route table.
Section 06

Azure Virtual WAN

Azure Virtual WAN is a managed hub-and-spoke networking service that simplifies connecting many VNets, branches, and remote users through one central hub — without manually managing VNet peerings or route tables.

  • Automatically manages transitive connectivity (A↔B↔C — all can reach each other).
  • Integrates VPN (site-to-site, point-to-site), ExpressRoute, and VNet connections in one hub.
  • Two SKUs: Basic (S2S VPN only) and Standard (VPN + ExpressRoute + VNet peering + Azure Firewall).
  • Best for large enterprises with 10+ branch offices or 20+ VNets.
For simple setups (2–5 VNets), stick with manual VNet Peering. Virtual WAN has overhead and cost that only pays off at scale.
