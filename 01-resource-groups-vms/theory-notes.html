Section 01

Azure Management Hierarchy

Every Azure resource lives inside a strict hierarchy. Understanding this hierarchy is the first step to managing access and costs correctly.

🏢

Azure Tenant

Your organization's dedicated Azure AD (Entra ID) instance. One per company.

🗂️

Management Groups

Optional grouping of subscriptions — useful for large enterprises with many teams.

💳

Subscription

Billing boundary. Each subscription has its own invoice and resource quota.

📁

Resource Group

Logical container for related resources — e.g., all resources for one application.

⚙️

Resource

Individual Azure service — a VM, Storage Account, VNet, etc.

Analogy
Think of it like a company's filing system: Tenant = the company building, Subscription = a department with its own budget, Resource Group = a project folder, Resource = individual documents inside that folder.
RBAC Inheritance
Permissions assigned at a higher level (e.g., Subscription) automatically flow down to all Resource Groups and Resources within it. You can always restrict further at a lower level.
Section 02

Resource Groups

A Resource Group (RG) is a logical container that holds all the Azure resources for a solution. It is not a VM or network — it is just a grouping mechanism.

Key Facts

  • Every Azure resource must be in exactly one Resource Group
  • Resources in one RG can connect to resources in other RGs
  • Deleting an RG deletes all resources inside it — be careful!
  • An RG has a region (metadata location), but resources inside can be in different regions
  • You can apply Tags to RGs to track cost by project, team, or environment

Best Practices

  • Group resources that share the same lifecycle — deploy together, delete together
  • Use naming convention: rg-appname-environment-region e.g., rg-webapp-prod-eastus
  • Create separate RGs for Dev, Staging, and Production
  • Avoid putting resources with different lifecycles in the same RG

Resource Group vs. Subscription

FeatureResource GroupSubscription
PurposeLogical grouping of resourcesBilling & quota boundary
BillingNo separate billSeparate invoice per subscription
NestingResources go inside RGRGs go inside Subscription
DeletionDeletes all resources insideDeletes all RGs and resources
Exam Tip
In AZ-104, questions often test whether you know that a resource belongs to exactly one RG, and that deleting an RG deletes everything in it.
Section 03

Azure RBAC — Role-Based Access Control

RBAC is how Azure controls who can do what on which resources. Instead of giving raw keys, you assign roles to identities at a specific scope.

The Three Elements of RBAC

ElementWhat it isExample
Security PrincipalWho is getting accessUser, Group, Service Principal, Managed Identity
Role DefinitionWhat actions are allowedOwner, Contributor, Reader, or custom role
ScopeWhere access appliesManagement Group, Subscription, Resource Group, Resource

Built-in Roles

OWNER

Owner

Full access to all resources. Can manage access (assign roles) to others.

CONTRIBUTOR

Contributor

Create and manage all resources. Cannot grant access to others.

READER

Reader

View all resources. Cannot make any changes.

CUSTOM

Custom Role

Define exactly which actions are allowed. Powerful for least-privilege setups.

RBAC Scope — Where does the role apply?

A role assignment is always tied to a scope. The tightest scope wins, and you can assign different roles at different levels:

  • Management Group — applies to all subscriptions under it
  • Subscription — applies to all RGs and resources in the subscription
  • Resource Group — applies only to resources in that RG
  • Resource — applies only to that specific resource
Least Privilege Principle
Always assign the minimum role at the narrowest scope. Don't give Owner at Subscription level when Reader at Resource Group level is enough. This reduces risk if an account is compromised.
Section 04

Azure Entra ID (formerly Azure Active Directory)

Azure Entra ID (previously called Azure Active Directory or Azure AD) is Microsoft's cloud-based identity and access management service. It is the foundation of all authentication in Azure.

Key Concepts

  • User — a person with a username + password in Entra ID
  • Group — a collection of users; assign roles to the group instead of individuals
  • Tenant — your organization's dedicated Entra ID directory
  • Service Principal — an application identity (non-human) used by apps/scripts
  • Managed Identity — like a Service Principal but automatically managed by Azure

Entra ID vs. Traditional Windows AD

FeatureAzure Entra IDWindows Active Directory
TypeCloud-based (SaaS)On-premises (Domain Controller)
ProtocolHTTP/HTTPS, SAML, OAuth 2.0, OIDCLDAP, Kerberos, NTLM
AuthenticationWeb apps, M365, Azure PortalDomain-joined machines, network logon
StructureFlat (no OUs/forests)Hierarchical (OUs, domains, forests)

Multi-Factor Authentication (MFA)

MFA requires users to verify with a second factor (e.g., phone app, SMS). Entra ID supports MFA and Conditional Access — rules like "require MFA when logging in from outside India."

Free vs. P1 vs. P2 Tier
Entra ID Free comes with every Azure subscription. P1 adds Conditional Access and Group-based access. P2 adds Identity Protection and Privileged Identity Management (PIM). IIMT students use the Free tier.
Section 05

Managed Identities

A common problem: your application running on Azure needs to access a Storage Account or Key Vault. You could hardcode a password — but that's a security risk. Managed Identities solve this.

How it works

Azure automatically creates an identity for your resource (VM, App Service, Function, etc.). You then assign an RBAC role to that identity on the target resource. The app can authenticate without any stored credentials.

TypeWhat it isUse case
System-assignedTied to one resource; deleted when resource is deletedOne VM needs access to one storage account
User-assignedIndependent identity; can be assigned to multiple resourcesMultiple VMs sharing same access to a Key Vault
Analogy
Think of Managed Identity like a company ID badge. The badge is tied to your role in the company (not your personal ID). You show the badge to enter the server room — no password needed. When you leave the company, the badge is cancelled automatically.
Section 06

Creating a Virtual Machine — Step by Step

Here is the process of creating an Azure VM through the portal. (Full VM deep-dive is Module 03.)

  1. Go to portal.azure.com → click "Create a resource" → "Virtual Machine"
  2. Basics tab: Choose Subscription, Resource Group, VM Name, Region, Image (OS), Size
  3. Authentication: Choose SSH public key (Linux) or Password (Windows)
  4. Disks tab: Choose OS disk type — Standard HDD, Standard SSD, or Premium SSD
  5. Networking tab: Choose or create a Virtual Network, Subnet, and Public IP. Configure the Network Security Group (NSG) — allow port 22 for SSH or 3389 for RDP
  6. Management tab: Enable Auto-shutdown, Monitoring, Backup (optional)
  7. Review + Create: Azure validates the configuration. Click "Create" to deploy.
Naming Convention for VMs
Use: vm-purpose-environment-region e.g., vm-webserver-dev-eastus. Azure names can be max 15 chars for Windows VMs, 64 for Linux.

What gets created automatically?

When you create a VM through the portal, Azure automatically creates several supporting resources:

  • Network Interface Card (NIC) — connects VM to the VNet
  • Public IP Address — optional, for internet access
  • OS Disk — storage for the operating system
  • Network Security Group (NSG) — firewall rules
Section 07

Summary — Key Points

Hierarchy

Tenant → Management Group → Subscription → Resource Group → Resource

Resource Group

Logical container. Deleting it deletes everything inside. One RG per resource.

RBAC

Who (principal) + What (role) + Where (scope). Owner > Contributor > Reader.

Entra ID

Microsoft's cloud identity service. Users, Groups, Service Principals, Tenants.

Managed Identity

No stored passwords. Azure manages credentials for your app automatically.

VM Creation

Basics → Disks → Networking → Management → Review. NSG controls port access.
